## 2. Два документированных типа исходных меток

### A. Кресты на H50Z (labels.json)

JSON организован по точному имени BMP, например:

~~~json
{
  "EXAMPLE_ONLY_005.bmp": {
    "original_width": 320,
    "original_height": 320,
    "keypoints_count": 2,
    "keypoints": [
      {"label": "start", "x_px": 120, "y_px": 160},
      {"label": "f1", "x_px": 60, "y_px": 90}
    ]
  }
}
~~~

Это **пример структуры, не настоящие H50Z-координаты**. Метка **start** — начальная операторская точка, **f1…f8** — реперы/фидуциалы, **не** координатные маски всей линии. Пустой участок рядом с крестом нельзя автоматически размечать как физический фон. При сопоставлении проверяются **точное имя файла, размер BMP и границы координат**. Совпадающие имена BMP в разных подпапках считаются неоднозначными: их нельзя автоматически склеивать с метками.

### B. Разметка измеренных треков visualMetro (070_###)

Внутри кадров есть списки треков, измеренные XYZ-точки и соответствующие пиксельные отметки **в трёх разных проекциях 1/2/3**. Иногда секции в файле записаны в другом порядке, поэтому проекцию нужно определять по её явному номеру, а не по позиции в тексте. Это **редкие последовательности измеренных точек**, не готовые бинарные маски на всех BMP. У них есть идентификаторы треков и можно исследовать 3D-геометрию при наличии достоверной калибровки и соответствующих изображений.

**Про «разметку девочек»:** доступные исходники подтверждают два формата выше, но не доказывают, что других материалов нет. Если у команды есть дополнительная ручная разметка масками/полилиниями, CSV, XML либо другой формат, его следует отдельно описать по 1–2 настоящим файлам с их исходными BMP. Не подменяйте такой файл измерениями film070 без проверки.

## 3. С чего начать, если BMP очень много

Сначала не обучаем модель на всём массиве, а делаем **инвентаризацию**: количество 8-битных BMP, неполные и неподходящие BMP, дубликаты названий, какие изображения имеют кресты, какие существуют без разметки, какие кадры visualMetro полные, какие разнесены по разным физическим запускам.

Рекомендуемая структура в **закрытом** каталоге (не внутри Git):

~~~text
/PRIVATE/
  H50Z/
    H50Z_030_01_005.bmp
    H50Z_030_01_006.bmp
    labels.json
    ...
  1mH2Data/S1/
    070_008/
    070_009/
    ...
  results/
~~~

Проверка и раздельные агрегированные/приватные выводы:

~~~bash
python scripts/research/bubble_chamber/physicists_data_intake.py \
  --bmp-root /PRIVATE/H50Z \
  --crosses /PRIVATE/H50Z/labels.json \
  --visualmetro-root /PRIVATE/1mH2Data/S1 \
  --public-summary /PRIVATE/results/input_counts_safe.json \
  --private-index /PRIVATE/results/source_index_PRIVATE.json
~~~

Если есть только BMP, уберите **--crosses** и **--visualmetro-root**; скрипт не будет выдумывать отсутствующую разметку. Для кадров visualMetro можно отдельно использовать существующие **scripts/research/bubble_chamber/ingest_visualmetro_sparse.py** и **bubble_chamber/visualmetro_import.py**.

**Публичный итог** содержит только числа. **Приватный индекс** содержит названия BMP, координаты крестов и происхождение измерений. Положите его только на закрытый носитель.

### Просмотр на собственных BMP прямо сейчас

~~~bash
python scripts/research/bubble_chamber/physicists_batch_preview.py \
  --bmp-root /PRIVATE/H50Z \
  --crosses /PRIVATE/H50Z/labels.json \
  --roi-mode both --max-images 8 --per-image 4 \
  --private-out-dir /PRIVATE/results/bmp_quicklook_PRIVATE
~~~

Откройте локальный **/PRIVATE/results/bmp_quicklook_PRIVATE/index.html**. На одинаковых 192 × 192 пиксельных участках сравниваются **исходный BMP с операторскими крестами**, кандидаты классического **Hessian/ridge** и **OpenCV LSD**. Все линии **UNKNOWN**, никакого физического соединения. Это не обученная AZUNet, не полный S39/S56 и не доказанные треки. Без крестов используйте **--roi-mode grid**, без **--crosses**. Все картинки сохраняются **только в приватном каталоге**.

Чтобы просмотреть **именно исторические реальные H50Z-выделения** ANZA/S39/S57, потребуются соответствующие исходные H50Z, приватные модели и/или рассчитанные ранее артефакты. Их нет в публичном GitHub. Публичная [галерея](demo.html) показывает **искусственные схемы**, а не реальные пиксели H50Z.

## 4. Что делает алгоритм

1. Из BMP считывается uint8-пиксельный участок без уменьшения масштаба или загрузки сотен мегабайт целиком; отмеченные оператором start/f1…f8 сохраняются отдельным слоем.
2. Детектор ищет **ориентированные тонкие структуры**, создаёт отклик, псевдомаску и открытые 2D-полилинии. Используются классические Ridge/Hessian/Frangi либо обученная U-Net/AZUNet **только при наличии валидной модели**.
3. Graph-LIRA строит возможные пары концов, учитывает расстояние, направленность касательной, кривизну и конфликты связей; сохраняет исходные фрагменты и предлагает **обратимые 2D-гипотезы**, а не новые доказанные треки.
4. Выход для физиков: исходный кадр, кандидаты линий, псевдомаска **1=предполагаемая линия, 0=предполагаемый фон, 255=UNKNOWN**, предложения соединений и предупреждения. Псевдомаска не является экспертной GT.
5. Специалист отдельно подтверждает **track / artifact / unknown** на линии и **same_track / different_track / unknown** для выбранной пары. Необработанная неоднозначность остаётся неизвестной.

Для S39 на реальных H50Z получены 567 предложений линий, 37 выбранных моделью соединений, 35 компонентов — **ни один не подтверждён физиком**. В экспериментах S28/S72 известная синтетическая GT позволила измерять восстановление искусственно вставленных треков. Это **не** native H50Z precision/recall. S84/S85 не доказали безопасного улучшения при полном восстановлении, S72 сохранён как baseline.

## 5. Как разработчикам встраивать в свою систему

Контракт: **192×192 uint8 grayscale → Detector.detect(image) → список N×2 точек (x,y) в том же кропе → Graph-LIRA → обратимые UNKNOWN-предложения**. Детектор может быть свой — ANZA не является обязательной частью интерфейса.

- [Контракт](../../../bubble_chamber/interop_api.py) и [демонстрация с чужим детектором](../../../scripts/research/bubble_chamber/example_verified_external_detector.py).
- [Конвертация координат в исходный BMP](../../../bubble_chamber/interop_coordinates.py): храните смещение ROI (x0,y0), не делайте молчаливого масштабирования.
- [Проверка модели/калибровки](../../../bubble_chamber/interop_verified_runtime.py): детектор, версия модели, SHA-256 весов, train-domain и отдельный источник CAL должны совпадать.
- [Путь обученной AZUNet в Graph-LIRA](../../../scripts/research/bubble_chamber/example_anza_to_graph_lira.py) — без приватного checkpoint это только интерфейсный smoke.
- [Система экспертного просмотра S19](../S19_REAL_H50Z_EXPERT_ANNOTATION_2026_10_25.md): операторские решения и ручное уточнение.
- [Подробный интерфейс](../DEVELOPER_INTEGRATION_2026_10_28.md), [проверенные результаты](../PHYSICISTS_RESULTS_2026_10_29.md).

Нельзя автоматически переносить scorer и пороги S72 на LSD/другую модель. Для каждого нового детектора обучайте scorer отдельно и фиксируйте порог на CAL **до TEST**. S56 ожидает минимум три фрагмента, иначе может вернуть 0 соединений даже при реально совместимой паре. При ошибке, неоднозначности или нарушенном source-identity — **отказ от стыка**. Для MILP нужен внешний дедлайн; время отдельного вызова не равно общему времени запроса.

## 6. Как получить научный результат дальше

1. Верифицировать перечень BMP и разбить по **физическим запускам**, не по случайным кропам одного фото.
2. Снять пробный приватный просмотр выделений на типичных/трудных участках: тонкие слабоконтрастные линии, разрывы, пересечения, царапины, реперы, разные плёнки.
3. Попросить физиков **подтвердить/опровергнуть небольшую стратифицированную выборку уже предложенных** линий и связей; не требовать вручную отрисовывать всё с нуля. Если приоритетные случаи отсутствуют, дополнять новые треки выборочно.
4. Если существуют соответствия **film/frame/view → конкретный BMP**, их должен явно зафиксировать оператор и проверить координаты/проекции. Если нет — visualMetro и H50Z остаются двумя **раздельными** источниками.
5. Выделить независимый TEST из других запусков; сравнить Hessian/Frangi/Steger, U-Net/AZUNet и Graph-LIRA с общей разметкой по *верным/ложным* стыкам, полноте треков, риску и времени ручной проверки. Отчитываться с интервалами по независимым событиям.
6. До независимого native GT — **только read-only/shadow mode**. Не утверждать ни конкретную частицу, ни импульс/массу, ни 3D-траекторию по единственному 2D-кадру.

## 7. Что запросить у команды физиков

Каталог BMP и запуска/плёнки, существующий labels.json с крестами, измерения visualMetro (или образцы **иной** разметки), точный способ сопоставления проекции с BMP, несколько экспертно проверенных примеров **same/different** и **track/artifact**, плюс разрешение на закрытый анализ. Это достаточный следующий практический этап; исходные приватные файлы **не отправлять в публичный репозиторий**.


## 8. Если физики установили соответствие visualMetro и трёх BMP-проекций

**Это не автоматический поиск по похожим именам.** Для использования 070-точек как меток конкретного изображения оператор должен вручную подтвердить точный исходный физический запуск, кадр и три оптические проекции 1/2/3, а также документировать идентификатор подтверждения. Для этого в репозитории есть [шаблон операторского сопоставления](OPERATOR_STEREO_MAP_TEMPLATE.json) с намеренно выключенной декларацией.

В своей приватной копии замените имена файлов на относительные пути внутри каталога BMP, укажите источник подтверждения и только после этого установите поле **operator_declares_same_physical_frame_and_view: true**. Затем запустите проверку:

~~~bash
python scripts/research/bubble_chamber/physicists_data_intake.py \
  --bmp-root /PRIVATE/STEREO_BMP \
  --visualmetro-root /PRIVATE/1mH2Data/S1 \
  --stereo-map /PRIVATE/operator_stereo_map_PRIVATE.json \
  --private-index /PRIVATE/results/verified_pairs_PRIVATE.json \
  --public-summary /PRIVATE/results/pair_counts_safe.json
~~~

Программа проверит три **разных** существующих BMP, размер изображения и границы всех измеренных 2D-точек/реперов. Протокол всё ещё сообщает **операторскую декларацию, не независимую истинную физическую идентичность**: размер и попадание координат в кадр ничего не доказывают о калибровке камеры или соответствии физического события. Пары и координаты остаются в приватном JSON, а публичный файл содержит только агрегаты.

Если сейчас существуют только кресты и большие H50Z BMP, **не пытайтесь привязать к ним 070 по названию**. Сначала выполняйте предпросмотр без экспертной GT, потом отдельно получайте доказанное соответствие.

## 9. Портирование на новую версию OpenCV

Новый BMP-предпросмотр использует **OpenCVLSDDetectorCompat** из [bubble_chamber/interop_detectors_cv5.py](../../../bubble_chamber/interop_detectors_cv5.py). Он нормализует выдачу OpenCV 4/5 из форм (N,1,4) и (N,4), не затрагивая исследовательский замороженный baseline **opencv-lsd-v1**. При переходе к собственному обученному графовому scorer этот v2-детектор считается **другой версией детектора**, поэтому требуется **новая TRAIN/CAL привязка и модель**, а не перенос старых порогов S72/S85.
