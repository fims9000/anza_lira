# S95 — размечаем ВСЁ, определяем тип, не удаляем короткие настоящие треки

**Ветка:** \`feature/bubble-s95-all-object-typing-operator-curves-2026-11-06\` (продолжение S94 → S93 → S92, основная пузырьковая ветка не меняется).

## Постановка задачи физиков

Вместо *«детектор нарисовал любую тёмную линию → это трек»* и вместо *«короткие линии похожи на мусор → удалить»* делаем два независимых уровня:

1. **Полное сохранение того, что извлекла S86:** S87 объединяет только действительно соседние пиксели на границах тайлов; S92 предлагает, но не подтверждает связи через пробелы. S95 сохраняет **каждый извлечённый S86 фрагмент**, включая короткий, сомнительный, пересекающийся и закрученный.
2. **Машинные типы для последующей экспертной проверки:** признаки формы, близость к человеческим меткам, множественные пересечения и (когда точно привязана к фотографии) операторская опорная кривая. Никакие пиксели исходного фото не удаляются и не становятся «доказанным фоном».

### Шесть классов отображения

| Машинная категория | Что означает | Что НЕ означает |
|---|---|---|
| \`CALIBRATION_CROSS_CONTEXT\` | Линия близко к человеческой метке репера \`f1..f8\` | Не утверждает, что **весь** фрагмент — крест и на нём нет трека |
| \`TRACK_LIKE_CANDIDATE\` | Продолжительный или согласованный с опорной операторской кривой отрезок | Не подтверждает принадлежность определённой частице |
| \`ARTIFACT_LIKE_CANDIDATE\` | Короткая угловатая галочка, компактный «волосок», вероятный артефакт | Не означает, что можно удалить без проверки |
| \`BUNDLE_OR_INTERSECTION_REVIEW\` | В малом районе встретились/пересеклись несколько разных фрагментов | Геометрия пока не отличает настоящий пучок от простого наложения 2D линий |
| \`COILING_TRACE_CANDIDATE\` | У линии большой последовательный направленный поворот: завиток/спираль | Не доказывает, что причиной является нейтрон, что известен тип частицы или есть 3D спираль |
| \`UNKNOWN\` | Короткая гладкая линия или неразрешённая структура | Не «фон»: весь кандидат остаётся доступным физику |

**Многометочные признаки сохраняются отдельно**: завиток может находиться рядом с вершиной, а прямая линия — пересекаться с реперным крестом. Базовый цвет для отображения один, но все причины записаны в \`all_morphology_tags\`.

Метаданные об исходной разметке (в S94) добавляют именно геометрический контекст: \`start\` — отмеченная человеком точка/вершина, \`f1..f8\` — реперная отметка. Она не заменяет экспертного контура или 2D маски частицы.

## Паробола от начала до конца — да, но только при достаточных данных

Для **произвольного направления** 2D трека правильнее использовать параметрическую форму (она работает и для вертикальных дуг):

\`\`\`text
P(t) = (x(t), y(t)),              0 <= t <= 1
x(t) = cx + bx * t + ax * t²
y(t) = cy + by * t + ay * t²
\`\`\`

Если известны только две конечные точки \`A,B\`, они не определяют \`ax,ay\` — таких парабол бесконечно много. При наличии последовательности измеренных человеком точек можно получить модель **с точно фиксированными концами**:

\`\`\`text
P(t) = (1-t) A + t B + t(1-t) K
\`\`\`

\`K\` оценивается по промежуточным измерениям. Это параметрическая парабола и одновременно нормированный геометрический *guide*. Если экспертный набор точек закручивается слишком сильно и RMS такого приближения высок, S95 **отказывается насильственно заменять спираль параболой** и сохраняет исходную измеренную ломаную.

Для заранее известных **операторских коэффициентов** S95 принимает точную локальную форму \`v(u)=a*u²+b*u+c\` вместе с началом локальной системы координат и осями \`u,v\`, либо 2D параметрическую \`x(t),y(t)\`. Проверяется, что вычисленные концы действительно совпадают с заявленными стартом и концом в исходных пикселях. Нельзя интерпретировать локальную параболу как глобальную \`y(x)\` без её осей.

**Доступные исходные данные:**
- старый H50Z \`labels.json\` размечает реперы \`f1..f8\` и \`start\`, *не* коэффициенты этих кривых;
- в VisualMetro есть действительно измеренные оператором отдельные треки \`e1t00, e1t01, e1t02t01, ...\` и последовательности соответствующих точек для трёх видов, поэтому на **своих проверенных фотографиях** их можно подставить в S95 как \`measured_points\`;
- прежние H50Z и film-070 относятся к разным наборам. **Нельзя автоматом переносить контуры 070 на H50Z 405 только потому, что у обоих есть координаты.**

Каждый source-locked операторский guide должен иметь точное \`source_bmp_name\`, \`source_bmp_sha256\`, размеры кадра и вручную подтверждённое соответствие изображения. Эти условия не позволяют сделать вид, что пользовательские точки 070 принадлежат снимку H50Z.

### Пример формата операторской кривой (ИСКУССТВЕННЫЕ значения)

\`\`\`json
{
  "schema": "S95_EXPLICIT_OPERATOR_2D_CURVES_V1",
  "source_bmp_name": "H50Z_030_01_405.bmp",
  "source_bmp_sha256": "REPLACE_WITH_EXACT_SOURCE_SHA256",
  "image_shape_yx": [384, 512],
  "explicit_photo_alignment_verified": true,
  "curves": [
    {
      "track_id": "manual_01",
      "kind": "parametric_quadratic",
      "start_xy": [25, 55],
      "end_xy": [330, 55],
      "x_coefficients_c_b_a": [25, 305, 0],
      "y_coefficients_c_b_a": [55, 0, 0]
    }
  ]
}
\`\`\`

Это тестовый пример, **не реальная разметка 405**. Альтернативный \`"kind": "measured_points"\` принимает \`points_xy\`, \`start_xy\` и \`end_xy\` для одного **уже идентифицированного оператором трека**. S95 возвращает значение RMS и отказывается выдавать плохо согласованную параболу за правильную траекторию.

## Запуск вообще без больших BMP (на сохранённом S86/S92)

\`\`\`bash
git fetch origin
git switch feature/bubble-s95-all-object-typing-operator-curves-2026-11-06
python -m pip install -r docs/bubble_chamber/requirements.txt

python scripts/research/bubble_chamber/physicists_s95_all_classes.py \
  --s86-dir /PRIVATE/results/H50Z_405_S86 \
  --s92-dir /PRIVATE/results/H50Z_405_S92 \
  --private-out-dir /PRIVATE/results/H50Z_405_S95 \
  --labels /PRIVATE/H50Z/labels.json
\`\`\`

Если S92 был построен с исходным \`labels.json\`, S95 требует этот же файл и SHA. **Когда и S86/S92 вообще недоступны, метаданные сами по себе не позволяют угадать пиксели и треки.** S94 умеет проверить только отдельный \`labels.json\`.

Сохранённые результаты:
- \`S95_ALL_OBJECTS/all_source_fragment_types.ndjson\` — каждый исходный извлечённый сегмент, все флаги, тип, связь с человеческим guide;
- \`S95_ALL_OBJECTS/human_operator_mark_locations.ndjson\` — координаты реперов и стартовых точек отдельно от треков;
- \`S95_ALL_OBJECTS/operator_2d_curve_guides.ndjson\` — параметрические или измеренные человеком контуры, только при подтверждённой привязке фото;
- \`S95_ALL_OBJECTS/all_gap_proposals_unknown.ndjson\` — все исходные гипотезы S92, без принятия физической связи;
- \`S95_ALL_OBJECTS/report.json\` и локальная страница \`index.html\`.

## Запуск для реального H50Z, чтобы увидеть все категории цветом

\`\`\`bash
python scripts/research/bubble_chamber/physicists_s95_all_classes.py \
  --bmp /PRIVATE/H50Z/H50Z_030_01_405.bmp \
  --labels /PRIVATE/H50Z/labels.json \
  --private-out-dir /PRIVATE/results/H50Z_405_ALL_CLASSES \
  --method s88-steerable \
  --max-side 2048
\`\`\`

При наличии **верифицированного файла операторских параметров того же самого кадра** добавить \`--operator-curves /PRIVATE/H50Z/verified_operator_curves.json\`.

В папке \`S95_ALL_OBJECTS/\` появятся:
- **\`S95_all_classes_comparison.jpg\`** — слева уменьшенный оригинал, справа **все** извлечённые фрагменты с цветами и опорной геометрией (ничего не скрываем как в S92 clean view);
- \`S95_original_small.jpg\` и \`S95_all_extracted_types_small.jpg\`;
- \`report.json\`, SHA и список всех источников.

Палитра на изображении:
**оранжевый — область реперного креста; голубой/бирюзовый — трекоподобная линия; красноватый — вероятный артефакт; фиолетовый — пучок/пересечение; зелёный — закрученная кривая; серый — неизвестно.** Жёлтый пунктир — **операторская опорная кривая**, а не изображение, обнаруженное машиной; пурпурный — **предложение S92 соединить разрыв**, а не физически подтверждённый трек.

## Оценка качества и что ещё улучшать

1. **Найти все строки:** исходный S86 надо настроить для коротких линий, отдельно учитывать тайлы с \`fragment_extraction_skip_reason\` — S95 не может восстановить не попавшие в S86 пиксели. Не поднимать уверенность только из-за количества нарисованных линий.
2. **Точно различать крест/пучок/пересечение:** добавить реальные 2D маски или полилинии экспертных классов вокруг каждой неоднозначной точки. Пока S95 видит только расположение операторского репера и геометрическое скопление разных фрагментов.
3. **Защищать короткие настоящие следы:** отдельно измерять, сколько подтверждённых коротких треков S92 почистил ошибочно. S95 перестал скрывать их в общем типизированном слое.
4. **Связь пунктирных треков:** оценивать \`same-track / different-track / unknown\` на экспертно подтверждённых парах, различая физическое совпадение и красивую геометрическую интерполяцию.
5. **Завитушки/спирали:** отдельное представление кривизны на нескольких масштабах и модели спиральных/круговых дуг. **Не требовать от них хорошей одной параболы**. Если фото отсутствует, нельзя количественно проверить качество их обнаружения.
6. **Стерео и физика:** H50Z + visualMetro film-070 нельзя смешивать. После проверки связи конкретного события и оптики можно переносить проверенные 2D guide в 3D реконструкцию.

Никаких новых реальных H50Z метрик, физических идентификаций или медицинских/ядерных выводов S95 пока **не** заявляет. Код проверен на синтетических фото и строгом исключении смешения источников.
